# Mobile Monitor (crash + API reporting) — design

Extends @upande/mobile-kit (npm) and upande_mobile (Frappe). Public, community-facing: no internal names, hosts or keys. Builder's calls unless marked.

## Goal
Sentry-style crash and error reporting for Expo apps that use the kit, shown on a Frappe www portal dashboard for IT admins and developers: failing API requests with URL, method, headers, payload and response; full device details (OS, model, battery, storage, network, app/runtime/OTA versions, locale...); who was logged in; breadcrumbs. Must not slow the app.

## Decisions (builder's calls)
- **Redact before it leaves the phone** (and again on the server): Authorization, Cookie, Set-Cookie, any header/key/field matching token|secret|password|passwd|pwd|api_key|apikey|authorization|session|sid|otp|pin|cvv|card; Frappe login bodies (`usr`,`pwd`). Bodies capped (default 8 KB, JSON-aware truncation), binary/multipart bodies replaced by a size note.
- **What is sent:** every crash/unhandled error (full), every failed API call (status>=400, network error, timeout; full detail), successful calls NOT sent by default (config `monitor.sampleSuccess`, default 0; sampled ones metadata only, no bodies). Per-app config: `monitor.enabled`, `captureBodies`, `redactKeys` (extra), `maxBodyBytes`, `breadcrumbs` (default 30), `ignoreUrls`.
- **Speed:** hot path only pushes a small object onto an in-memory ring buffer (bounded, drop-oldest). No JSON.stringify, redaction or device probing on the request path. Redaction + serialisation happen in the flush, off the interaction path (InteractionManager/idle, setTimeout). Flush: every 30 s when non-empty, at 20 events, on app background; one batched POST, gzip not required; offline queue persisted (capped, e.g. 100 events / 1 MB) and drained when online; backoff on failure; dedupe repeated identical errors within 60 s into a count; hard cap per session (default 200 events). Device snapshot collected once per launch (cheap static facts) and the dynamic part (battery, storage, network, memory) read async at event time with a 1 s timeout, cached 30 s. All native probes are optional (expo-device, expo-battery, expo-network, expo-file-system disk space) via safe probes; missing module => field omitted.
- **Auth:** reports need a signed-in Frappe session (events before login are queued and sent after). Optional per-Mobile-App flag `accept_reports_before_sign_in` (default off) allowing guest ingest, rate-limited by IP and size-capped, for login failures. Server files rows under the session user, never one the client claims; server also records observed IP.
- **Grouping:** server fingerprint = sha1(kind + normalised message + top 3 stack frames, or method+path template+status for API errors) -> Mobile Issue (status Open/Resolved/Ignored, count, users_affected, devices_affected, first/last seen, last version). Reopens when a resolved issue recurs on a newer version.
- **Retention:** events 30 days (Mobile App field `event_retention_days`), issues kept; daily purge job in batches. Dashboard queries are indexed and paginated.
- **Dashboard:** www portal page `/mobile-monitor` (System Manager only), vanilla JS + JSON from whitelisted endpoints, light/dark, mobile friendly: Overview (events/issues by day, top issues, affected devices), Issues list (filter app/status/version/level/search), Issue detail (latest events, stack, breadcrumbs, request/response viewer with copy-as-curl without secrets, device panel, user), Devices health (low battery, low storage, outdated OS/app, offline), per-device timeline. Bodies rendered as text (escaped) — never as HTML.
- **Privacy:** capture of bodies and user details is configurable and documented; a user-visible kill switch `setMonitoringEnabled(false)`.

## Wire contract
POST `/api/method/upande_mobile.api.monitor.ingest`, form field `payload` = JSON string:
`{ "app": "<Mobile App name>", "install_id": "...", "sent_at": ISO, "events": [Event, ...] }` (max 50 events, 512 KB)
Event: `{ id, kind: "crash"|"error"|"api"|"log", level: "fatal"|"error"|"warning"|"info", ts (ISO UTC ms), message, name?, stack?, fatal?, count?, screen?, session_id, app_version, runtime_version, update_id?, breadcrumbs: [{ts,type,message,data?}], request?: {method,url,status,duration_ms,request_headers,request_body,response_headers,response_body,truncated,error?}, device: DeviceFacts, user?: {id,full_name,roles[]}, extra? }`
DeviceFacts (all optional): platform, os_version, os_build, brand, model, device_name, is_physical_device, battery_level (0-1), battery_state, low_power_mode, storage_free_bytes, storage_total_bytes, memory_total_bytes, network_type, is_connected, is_internet_reachable, carrier?, locale, timezone, screen {width,height,scale,font_scale}, orientation, app_state, color_scheme, js_engine, build_type (embedded|ota|dev), install_id, device_key (raw android id; server hashes).
Response: `{ "message": { "accepted": n, "dropped": n, "next_flush_ms": n } }`.
Dashboard endpoints (System Manager): `upande_mobile.api.monitor.overview|issues|issue|events|devices|set_issue_status|purge_now`.
